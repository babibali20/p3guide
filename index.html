Project 3 — Linux Boot Steps

Reference sheet — readable from Ubuntu's own browser once you're connected to WiFi
Goal of this page: get the iPad from DFU mode into a "PongoOS" shell for the first time, using the real palera1n tool on real (non-virtual) Linux. That's the only thing this covers. Uploading the kernel/module is a separate step after this is confirmed working.

1 Boot into the USB

  1. Start menu → Power → Shut down (full shutdown, not restart)
  2. Press the power button
  3. The instant it powers on, tap Esc repeatedly (HP Startup Menu)
  4. Press F9 for Boot Device Options
  5. Arrow keys → select the USB drive → Enter
  6. At Ubuntu's screen, choose "Try Ubuntu" — never "Install Ubuntu"

2 Connect to WiFi

  1. Click the network icon, top-right of the screen
  2. Select your WiFi network, enter the password, connect

3 Open a Terminal

  1. Click "Activities" (top-left) or the search icon
  2. Type terminal, open it

4 Download and verify the exact tool

Paste each line, press Enter after each:

cd ~/Desktop
wget https://github.com/palera1n/palera1n/releases/download/v2.0.0-beta.9/palera1n-linux-x86_64
chmod +x palera1n-linux-x86_64
sha256sum palera1n-linux-x86_64

Output must match exactly:

5b6dec3a7ee15b14e989466a098d02edeb8455070009ffaa228caf2b3298dbd8

If it does not match exactly — stop and report back before continuing.

5 iPad into DFU mode

  1. Plug the iPad into the laptop via USB
  2. Hold Power + Home together for exactly 8 seconds
  3. At 8 seconds, release Power only, keep holding Home for 5 more seconds
  4. Screen must stay completely black the whole time. Apple logo appearing = failed, just retry.

6 Safe check (no changes made)

./palera1n-linux-x86_64 -I

Expect to see:

Mode: DFU
ProductType: iPad5,3
DisplayName: iPad Air 2 (WiFi)

If it hangs or shows nothing, the iPad dropped out of DFU — redo step 5.

7 The real step

./palera1n-linux-x86_64 -p

Then immediately go to Section 9 below and follow whichever branch matches what you see. Don't guess — find your exact situation in the list.

9 Troubleshooting — find what you're seeing

A. First, always run this one check:

lsusb

Look through the list it prints for a line containing 05ac (that's Apple's ID). Then go to the branch below that matches:

B. lsusb shows NOTHING with 05ac in it at all

The iPad isn't connected or isn't in DFU mode. Do this:

  1. Check the USB cable is firmly plugged in at both ends
  2. Try a different USB port on the laptop if one is free
  3. Redo DFU entry exactly: Power+Home 8 sec together → release Power only → hold Home 5 more sec → screen must stay pure black the entire time
  4. Run lsusb again after each attempt
  5. Repeat up to 5 times. If still nothing after 5 clean attempts, stop and note that — it's worth reporting, not normal.

C. lsusb DOES show an Apple device with ID 05ac:1227

Good — DFU mode is real and Linux sees it. Now run:

./palera1n-linux-x86_64 -I

Expected good output includes Mode: DFU and ProductType: iPad5,3.

  • If that text appears: go straight to branch D below.
  • If it hangs with no output, or only shows the startup banner and the usbmuxd warning with nothing after: press Ctrl+C to stop it, then try running it with elevated permissions instead: 
    sudo ./palera1n-linux-x86_64 -I
    (If it asks for a password and you don't have one set, just press Enter — the default Ubuntu Live session often has no password.)
  • If that still shows nothing after ~15 seconds: unplug the USB cable, wait 2 seconds, plug back in, redo DFU entry (step 5), and try the -I check again from the top of branch C. Repeat up to 3 times.

D. -I correctly shows Mode: DFU / iPad5,3 — now run the real exploit:

./palera1n-linux-x86_64 -p

(add sudo in front too if step C needed it: sudo ./palera1n-linux-x86_64 -p)

  • If it prints an error and stops before ever showing "Checkmate!": unplug the cable, wait 2 sec, replug, redo DFU entry (step 5), run -p again.
  • If it shows "Checkmate!" and then "Timed out waiting for download mode": the exploit itself is WORKING — that's the hard part done. Go straight to Section 10 below, which is entirely about fixing exactly this.
  • If you see a wall of checkra1n/Pongo-style text and it ends on a new prompt that just sits there waiting for input: that's success. Stop. Don't type anything else into it.

E. Once you have a real outcome (success, or you've worked all the way through Section 10 without success)

Screenshot or photograph exactly what the terminal shows. Boot back to Windows (top-right power icon → Restart, remove the USB when prompted). Come back to the same chat and show what you got — include which branch you ended up on, and roughly how many tries it took.

10 If "Timed out waiting for download mode" appears

This means the exploit already worked ("Checkmate!") — this is just a reconnect hiccup after it, not a real failure. Confirmed reliable now with: battery power (charger unplugged), a non-USB-3.0 port, direct connection (no hub), and the iPad and laptop in your current setup. Just unplug/replug (wait 5-10 sec), redo DFU entry, and run -p again — this has worked every time so far once the port was right.

11 You have a live PongoOS shell — now upload the real files

You already succeeded at the hard part. That "pongoOS 2.6.2-97c2800e" banner confirms it's the exact build our module was made for. This section gets our actual kernel/module files onto this Ubuntu session and runs them for real. It's a longer sequence — go slowly, one command block at a time.

Step 1 — Install GitHub's tool and log in (one-time)

sudo snap install gh --classic

The --classic is required — without it snap refuses to install gh at all.

sudo apt install -y git

gh needs git present on the system even though we're not using git commands directly — without this, gh auth login succeeds but every actual gh command afterward fails with "unable to find git executable".

gh auth login

Answer the prompts: GitHub.com → HTTPS → Login with a web browser. It will show a code and tell you to open a URL. Open Firefox, go to that URL, type the code, click Authorize. Come back to the terminal — it should say you're logged in.

Easy to miss: after entering the code, GitHub may show a "Confirm access" (sudo mode) screen instead of finishing right away. If you don't have GitHub Mobile linked, click "Send a code via email," check that inbox, and enter the code it sends. Skip this and the terminal just sits there forever looking like nothing is happening — it's actually stuck waiting on this confirmation.

Step 2 — Download the 4 real files (private) and our script (public)

mkdir -p ~/project3 && cd ~/project3
gh release download pongo-upload --repo babibali20/p3files
wget https://raw.githubusercontent.com/babibali20/p3guide/master/orchestrator_v3.py

If any of these don't match exactly, stop and report back.

Step 4 — Install the Python USB tools

sudo apt update
sudo apt install -y python3-usb libusb-1.0-0

Using python3-usb here (not pip3 install pyusb) is deliberate — last time, pip installed it only for the normal user, and since the script needs to run as root (via sudo) to access the USB device, root couldn't see it and every run failed with ModuleNotFoundError: No module named 'usb'. This apt package installs it system-wide, visible to root too.

If this exact error still appears anyway (ModuleNotFoundError: No module named 'usb' when running with sudo): run sudo pip3 install --break-system-packages pyusb instead — note the sudo before pip3 this time, which installs it for root directly.

Step 5 — Get a fresh live connection

From wherever you saved palera1n-linux-x86_64 (likely ~/Desktop):

cd ~/Desktop && sudo ./palera1n-linux-x86_64 -p

Wait for "Checkmate!" then the PongoOS banner. Based on your last two runs this now works reliably with your current port/cable setup — if you see "Timed out waiting for download mode," don't panic, it recovered on its own within a few seconds both times before. Once it prints "Booting PongoOS..." the command finishes and hands you back a normal terminal prompt by itself — there is nothing left running that needs closing, on the laptop or the iPad. Just continue to the next step.

Step 6 — Run our script for real

cd ~/project3
sudo python3 orchestrator_v3.py --dry-run --pkg-dir .

Must end with STATIC VALIDATION: PASS. If not, stop and report back.

sudo python3 orchestrator_v3.py --list-devices

Should show a device with VID=05ac PID=4141 (that's Pongo mode). If it shows nothing, the device likely isn't sitting in Pongo mode anymore — redo Step 5.

If that looks right, the real run:

sudo python3 orchestrator_v3.py --execute --pkg-dir .

This uploads our module, the kernel, the KPF, and the ramdisk, and issues the exact command sequence, printing every step live.
